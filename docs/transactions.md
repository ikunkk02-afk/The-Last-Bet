# 绿宝石事务与恢复（schema 2）

本阶段仅实现存取款与流水。全部资产操作在服务端主线程同步执行，客户端只能提交菜单编号、服务端会话 UUID、一次性令牌、白名单操作和流水页码，不能指定账户、玩家、币种或金额。1 / 16 / 64 / 全部的实际金额由服务端计算。

## 文件与不变量

| 文件 | 内容 |
| --- | --- |
| `data/lastbet_bank.dat` | 原有原生 SavedData 包装；`data.schema_version=2`，账户及完整成功流水 |
| `playerdata/<玩家UUID>.dat` | 原版玩家数据，加根字段 UUID `lastbet_transaction`，表示该玩家最近交易检查点 |
| `data/lastbet_transactions/<玩家UUID>/<交易UUID>.dat` | 独立 schema 1 事务日志；字符串 `state=PREPARED` 或 `state=COMMITTED` |
| 同名 `.dat_old` / `*.tmp` | 上一版本与失败写入证据；不得在运行中删改或自动替换主文件 |

事务日志包含唯一交易 UUID、账户 UUID、玩家 UUID、类型、正数金额、交易后余额、真实毫秒时间戳、账户内连续顺序号、前一检查点、变更前后 36 格主背包快照。快照使用原版物品及组件 NBT，排除副手、盔甲及其他容器。日志加载会重新计算物品变化，验证快照与交易金额一致。

银行账户保存最近检查点，与完整成功流水的末项对应。余额必须非负且不超出 `long`；流水顺序号决定发生顺序，系统时间回拨不会改变排列。流水唯一 UUID 不得重复，重放同一内容的提交不再改变余额。GUI 每页只下发最多 10 笔；完整历史与完成日志均保留，没有自动裁剪。

## 正常提交顺序

1. 验证玩家存活、非旁观者、当前菜单实例 / 编号、会话 / 一次性令牌、页面、维度、柜台存在与 8 格距离、账户状态、余额及主背包。复制物品并计算完整计划；取款先合并组件兼容的堆叠再使用空格。余额、容量不足或零金额直接拒绝，无成功流水。
2. 预检候选银行文件和事务日志能在现有 NBT 读取预算内完整回读。验证玩家内存检查点与银行一致，保存、回读交易前玩家状态。
3. 写入 PREPARED 日志并确认回读成功，此前不修改任何资产。
4. 应用服务端背包计划，设置玩家检查点，立即保存并回读玩家主文件。
5. 一次银行主文件写入提交新余额、唯一成功流水与银行检查点，回读确认。
6. 将日志持久化为 COMMITTED，完成回读后同步客户端并返回成功。

事务写入在同目录创建临时文件，压缩 NBT 写入后 `FileChannel.force(true)`，回读校验，再备份旧主文件并使用 `ATOMIC_MOVE` 替换，最后回读主文件。交易涉及的银行、玩家、日志写入不支持原子替换时直接报错，绝不降级普通移动。第一阶段发卡流程原有非事务写入接口仍保留，但存取款统一使用强制原子写入。`setDirty()` 和周期自动保存不是事务提交依据。

同步主线程步骤间不会插入原版 tick、玩家交互、死亡或自动保存。出现保存异常时立即锁定所有者，将当前玩家标为隔离并断开；在连接完全移除前屏蔽游戏报文、玩家 tick、伤害及死亡路径，防止不确定物品继续流转。银行文件写入失败同时触发原有全局银行停用保护；其他玩家仍可继续游玩。

## 恢复判定

服务端启动时扫描日志，在玩家进入世界前再次验证玩家主文件及检查点。每个玩家只允许一个未完成事务。不采用备份文件猜测恢复。

| 银行 / 玩家状态 | 动作 |
| --- | --- |
| 银行尚未提交；玩家前检查点且主背包匹配前快照 | 根据日志写入后背包和玩家检查点，再提交银行与流水，完成日志 |
| 银行尚未提交；玩家后检查点且主背包匹配后快照 | 跳过物品修改，只提交银行与流水，完成日志 |
| 银行已包含该 UUID；银行与玩家检查点一致 | 验证流水内容后只完成日志，不再修改物品、余额或追加流水 |
| 已 COMMITTED 的历史日志 | 验证其流水存在；入服验证玩家最新检查点，不用旧背包快照覆盖后续使用、掉落或死亡 |
| 主文件缺失 / 损坏、身份冲突、前后快照均不符或检查点冲突 | 锁定受影响账户并拒绝入服，保留文件与异常日志，等待管理员处理 |
| 无法识别归属的日志目录或根扫描失败 | 全局停止银行及玩家入服，避免遗漏未知事务 |

恢复过程使用相同持久化步骤，也可以再次中断；下一次启动按磁盘实际检查点继续，重复执行不会复制资产。PREPARED 持久化之后即使客户端没有收到成功，重启也可能完成该交易；客户端必须重新读取余额与流水，不能根据超时自行返还物品。

检查点通过正常玩家保存以及 Fabric `ServerPlayerEvents.COPY_FROM` 的死亡重生复制保留。单人整合服务器通常优先使用 `level.dat` 中的旧 `Data.Player`；已有交易检查点的玩家由入服预检明确加载经过校验的 `playerdata` 主文件，避免旧快照覆盖已提交的物品状态。

## 旧档升级

合法 schema 1 账户显式迁移为 schema 2，所有者、账户 UUID、银行卡 UUID、余额（包括非零余额）及待发卡状态原样保留；流水初始化为空，无交易检查点。下一次保存写为 schema 2。未知 schema、字段错误、负余额、重复身份或不一致流水明确报错并停用，不当作新世界重建。银行主文件缺失但有备份或事务目录时同样拒绝新建空银行。

## 管理员处理与限制

1. 停止服务器 / 关闭单人世界，保留完整世界副本和日志。查找 `Bank account locked` / `Bank disabled` / `Bank journal scan failed`，记录玩家 UUID、日志文件名中的交易 UUID、异常堆栈与失败阶段。事务文件的 `state`、银行末项和玩家检查点共同表示阶段。
2. 在副本中检查银行主文件、玩家主文件、该玩家全部事务日志及 `.dat_old` / `.tmp`。文件缺失和冲突时程序不会自动选择哪份正确，也不提供清零或跳过检查命令。
3. 优先恢复一次完整且一致的停服备份；银行、`playerdata`、事务目录与 `level.dat` 必须来自同一份世界快照。若只能人工核对，应保留原始证据、在副本中由了解 NBT 和协议的管理员核对，不能只恢复某一个文件。
4. 修复造成写入失败的磁盘权限 / 容量 / 文件系统问题后，在副本启动检查恢复日志，核对余额、物品与唯一流水，再开放正式世界。

现有读取限制为 `NbtAccounter` **64 MiB 分配预算**，不是压缩文件大小。候选银行 / 日志预检在修改资产前拒绝超限交易，明确显示存储容量提示并记录交易 UUID；历史绝不静默覆盖。完整历史集中在银行文件，预检、保存和启动扫描成本随历史增长；完成日志也持续占用空间。本阶段没有归档 / 清理工具，大型服务器应在达到预算前开发显式分段持久化与索引迁移。GUI 分页已实现，但不降低后台完整存储的成本。

原子替换与文件强制落盘不能保证所有硬件断电、磁盘缓存、文件系统目录元数据丢失场景。真实测试覆盖 JVM 强制终止，未模拟操作系统断电或物理损坏。不支持第三方直接修改资产、运行中替换文件、手动删除部分日志或只恢复部分世界文件；检测到不一致就停止交易。主线程同步多次落盘会增加延迟，慢磁盘和大历史需要评估，未进行规模性能基准测试。第三方模组对玩家保存、死亡和网络处理的 mixin 兼容性未验证。
